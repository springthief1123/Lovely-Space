## 判定と根拠の凡例

| 判定 | 意味 |
|---|---|

| 一致（静的確認） | 本家仕様は docs/site-protocol.md（2026-10-04採取が基礎）と採取記録に依拠し、コードと突き合わせて一致 |

根拠の種別は各行に [実地] [静的] [CI] [テスト] [docs] のいずれかで示す。

## 結論サマリー

1. **中核仕様（ジャンル・一覧解析・ページ送り・ID再利用/立て直し判定・検索・通信間隔・入室・チャット・作成者操作・公開ルーム）は、docs記載と静的に高い精度で一致**しており、今回の本家実地調査（ジャンル23件の名称と順序、6列構造、60件/ページ、作成フォーム項目、会員ログインフォーム）でも裏付けが取れた。
2. **ただし「正しく動作する」と確認できたのは単体テストとCIの範囲まで**である。本家実通信を伴う一連の動作（ロボット確認つき入室、作成者側ajax応答、再入室、会員Cookie共有）は、リポジトリ自身が `needs-device-test` / `needs-capture` として残している通り未検証で、本監査でも再確認できなかった（§C）。
3. **現行mainのピンは信頼性に重大な欠陥が6件あるが、その全てが未マージPR #186の修正対象**であり、PRのCIは成功し、CodexレビューのP1指摘も最終コミットで修正済みである。したがって最優先事項は新規開発ではなく **#186のマージと実機確認** である。
4. PR #186でも直らない恒常的な差異は、(a) 部屋作成のメール通知用 `email` 欄がアプリ入力画面に無い、(b) 「空き中のみのピン＋レーダー計画なし」では背景の周期確認が登録されない、の2件が中程度。その他は軽微な脆弱性候補と整理事項である。
5. 未実装項目（画像送信、会話ログ全文、人単位ブロック、入室者あり通知 #43、待ち受けモード #153、年齢認証）は **いずれもdocsの未対応宣言とコード実態が一致** しており、「実装済みと誤認させる」記述や実装は見つからなかった。Issue #48 が掲げる「本家機能の対応表」は本レポート §A で代替できる。

# B. 不一致・不具合候補レポート

重要度: 重大 = 誤通知・誤入室・データ喪失に直結 / 中 = 機能欠落や条件付きの誤動作 / 軽微 = 表記揺れ等への脆弱性、整理事項

## B-1.ピンの空き検知が短時間の「満室→空き→満室」を取りこぼす

- 現象: ピンした部屋が短時間だけ空いてすぐ満室に戻ると、空き通知・空き履歴・自動入室のいずれも発生しない。
- 再現条件: main `58f9f15`。ピンの処理が追いつく前に2回以上の観測が届くこと。
- 本家の期待動作: 本家に直接の仕様はないが、「空いたらもれなく知らせる」という製品仕様（PR #185 の題名）に対する不具合。
- 原因候補: `app/data/Pins.kt:176-182`（main）が `StateFlow` の観測を `conflate()` で処理し、中間状態が最新値に潰れる。順番待ち側は #177 で順序付きイベント化済みだったが、ピン側が追随していなかった。
- 修正方針: **PR #186 `85492b0` で修正済み**（順序付きイベント `RoomObservationJournal.changes` を逐次処理し、保存できるまで同一観測を再試行、背景Workerは処理完了を待つ）。マージと実機確認のみ残る。
- 関連テスト: PR追加 `rapidFullOpenFullObservationsStillNotifyTheIntermediateVacancy`。

## B-2.立て直し・手動引き継ぎがプロセス終了で失われ、誤通知・誤自動入室を招く

- 現象: (1) 立て直した部屋へピンが引き継がれる前にアプリが終了すると、移動イベントが消失し、知らせ方・メモ・空き履歴・自動入室設定が新部屋へ移らない。(2) 「似た部屋を同じ人として引き継ぐ」を承認した直後に再起動すると、その区別が消え、既に待機中の移行先を「新しく空いた」と誤認して通知し、自動入室まで開始し得る。
- 本家の期待動作: 類似部屋は「利用者が同じ人と答えるまで引き継がず、自動では入らない」（AGENTS.md 規則3）。(2) はこの歯止めの実質的な迂回になる。
- 原因候補: `RoomPreferenceRepository` の移動通知が1回きりの `SharedFlow` イベント、手動承認の記録 `adopting` がインメモリ集合のみ（いずれも main）。
- 修正方針: **PR #186 `1f37bf4` + `cc0e298` で修正済み**（移動を Room DB の `local_state` に永続キュー化し、種別 REBUILD/ADOPTED も同一トランザクションで保存、処理成功後にのみ消去）。Codexレビューが種別永続化の欠落を P1 として指摘し、最終コミットで解消、所有者がCI全成功を確認済み。
- 残存する軽微な点: 順序処理の再試行は無限ループ方式のため、保存が恒常的に失敗すると後続観測が頭打ちになる（データを落とさないための意図的なトレードオフ）。

## B-3.匿名ピン（満室で名前なし）が別人の部屋を「空いた」と誤認し得る

- 現象: 満室状態でピンした部屋（名前・性別が一覧に出ない）について、同じ room_id を別人が再利用し、募集文の異なる待機中部屋として現れると、本人の部屋が空いたと誤通知する。別人の募集文で保存スナップショットが書き換わる問題も付随する。
- 原因候補: 同一性照合 `core/RoomTracking.kt:6-13` は名前/性別/年齢のみを見て募集文を見ず、名前が片側不明なら AMBIGUOUS（=空き確定を止めない）になる。`core/PinWatch.kt`（main）はそのまま OPEN を返す。
- 修正方針: **PR #186 `645a26c` + `2e7f898` で修正済み**（名前なしピンで募集文が変わった同一IDは空き確定にせず UNSEEN とし、表示・保存側にも同ガードを追加）。
- PRでも残る限界: **募集文まで同一の別人は原理的に判別できない**。これは本家が満室時に名前を出さない仕様上の上限であり、不具合ではなく仕様限界として明記する。

## B-4.ピンのページ探査が弱く、見失った空き部屋を探し直せない

- 現象: 空きピンの載っていたページ情報がプロセス内にしかなく再起動で消失する。探査範囲も「載っていたページと次のページ」までで、2ページ以上ずれた部屋は追跡対象から外れる。加えて、別ページから消えた保留表示（carried）のみの部屋を「空いている」と誤表示し得る。
- 修正方針: **PR #186 `9a157c7` で修正済み**（最終ページ・総ページ数・探査位置を永続化し、全ページを巡回する探査に変更、carried のみの部屋は UNSEEN）。

## B-5.部屋作成のメール通知用 `email` 欄がアプリの入力画面に無い

- 現象: 本家の作成フォームには「メール（任意）」があり、入室時のメール通知に使えるが、アプリの作成入力画面には入力欄がなく、プリセットにも保存できない。
- 本家の期待動作: [実地] 作成フォームでメール欄と「メール通知機能の説明」リンクを確認。
- 原因候補: `app/ui/create/CreateRoomScreen.kt` の prefill 対象が name/sex/years/prefecture/message の5項目のみで、アプリ側の入力UI自体に email が無い。
- 影響の限定: 送信自体は本家フォームで行われるため、本家画面の全表示に切り替えれば直接入力は可能。ただし通常導線では使えず、プリセットで使い回すこともできない。
- 修正方針: 作成入力画面に任意項目として email を追加し、prefill 対象に加える（プリセット保存は「端末内にのみ保存する」前提と合わせて判断）。既存Issueに直接の対応は見当たらず、新規タスク化が妥当。

## B-6.空き中のみのピンは背景で追跡されない

- 現象: ピンが全て「空いている」状態で、背景レーダーの計画も順番待ちの未処理も無い場合、WorkManager の周期実行自体が登録されない。アプリを閉じている間にその部屋が満室→再度空きになっても、背景では検知できない（前面確認のみ）。
- 原因候補: `LovelySpaceApp.kt` の周期登録条件が「背景レーダー計画あり」または `waitlist.hasPendingWork()` のみ。満室ピンは順番待ち経由で含まれるが、空きピンは含まれない。
- 修正方針: 周期登録条件に「ピンが1件以上ある」を加えるか、仕様として「背景追跡は満室ピンと順番待ちのみ」と画面・設定に明示する。#153（待ち受けモード）・#46（背景機能の設定）と重なるため、同Issue内で扱うのが最小。
- 補足: 設定画面には「閉じている間は15分ごと」と説明があるため、利用者の期待との差が生じ得る点も合わせて見直す。

## B-7.満室セルの性別・年と隠し募集文の抽出が、本家の表記揺れに弱い

- 現象: 満室行の性別はセル全文が「男」「女」と完全一致した場合のみ判定され、年齢は数値変換のみ。隠し募集文の特定は `span.hearttext` の style 属性に `display:none` が含まれることに依存し、地域タグは「直接の子である最初の font.small」限定。
- 根拠: `core/RoomListParser.kt:107-108,114-118,121-125,135-136`。名前（heartmark）と募集文には専用処理があるのに、性別・年には同等の hearttext 分離がない。
- 影響: 本家が満室セルに装飾や余分な文字を足すと、性別 UNKNOWN・年齢なしに化け、同一性照合（§B-3）と絞り込みの精度が落ちる。現行の実地表示（満室行の性別・年齢が通常表示される例を確認）では直ちに壊れてはいない。
- 修正方針: hearttext 内テキストを優先抽出する形に性別・年も統一し、フィクスチャに表記揺れケースを追加する。

## B-8.細部の仕様差・未整備

1. 年齢の検証範囲: アプリは 18〜99 を許す（`core/ProfileValidation.kt`、入室は数値の自由入力）が、本家の作成フォームの年齢セレクトは [実地] 秘密+18〜90。入室前画面の選択肢が同範囲なら、91〜99 は本家で受理されない可能性がある（入室側は未確認のため候補止まり）。
2. 発言間隔の高負荷時ルール: 本家は負荷が高いと発言間隔が5秒になる（docs）が、アプリは1.5秒固定。サーバ側で拒否され得るだけで本家より攻撃的にはならないため実害は小さい。
3. HTTPタイムアウト: connect 15秒/read 30秒のみで write・全体（call）の上限が明示されていない（`ShaloveClient.defaultHttpClient`）。長時間ハング時の上限が OkHttp 既定依存になる。
4. `ShaloveClient.enter(captchaToken)`: トークンを3つの認証フィールドへ入れる直接POST経路があるが、呼び出し側は常に null を渡しており実質 dead code。コメント（「WebViewで得た値」）と実態が食い違う。削除するか、WebView経路専用である旨にコメントを直す整理事項。

## B-9.サイト側絞り込みの送信手段が残存し、到達経路が完全には閉じていない

- 事実: 2026-10-16 の決定で「見つける」は本家側絞り込みを使わないことになっているが、`RoomQuery.siteParams/toUrl`（vsex 等+検索語を Shift_JIS で送る実装）は現存しテストも残っている。現行の見つける経路が条件なしで取得することは確認した。一方で、レーダーの履歴・部屋確認（`RadarRoomInspection.kt:12`）と順番待ちの開始クエリ（`Waitlist.startQuery`）は、保存済みの `sourceQuery`（絞り込み付き RoomQuery であり得る）を復元して取得に使う構造がある。
- リスク: 旧バージョンで保存された絞り込み付きクエリが残っていると、その経路では本家側絞り込み付きで取得され、「一覧はジャンル全体だけを読む」という前提（ページ窓・閉室判定は全体一覧前提）で整合が崩れる可能性がある。新規に絞り込み付き sourceQuery が生成されるかは今回の調査では未確認。
- 修正方針: sourceQuery の復元時に絞り込みを落としてジャンル+ページだけにするか、生成・保存側で sourceQuery に条件を持たせないことをテストで固定する。あわせて docs の「使わず」という表現を実装実態に合わせて更新する。

## B-10.端末内保存の扱い

- ピン・順番待ちの保存（他利用者の名前・募集文を含むスナップショット）は SharedPreferences の平文JSON。進行中部屋の鍵（暗号化保存）とは扱いが異なる。端末内のみで外部送信はないため規約上の問題は小さいが、アプリロック等との整合として記録する。
- ジャンル定義と docs 表の完全一致を検証するテストがなく（キーの一意性のみ）、将来のジャンル追加・削除をテストで検出できない。

# C. 未確認事項・実機検証項目

各項目に「なぜ確認できなかったか」と「利用者が実施すべき具体的手順」を記す。手順は本家への影響を最小化するため、自分の部屋・自分の端末での確認を前提とする。

## C-1. 入室前画面の実フォームと一時ID
- 未確認: 待機者表示の文面、一時ID（端末種別+5文字）の持続期間、認証欄が出る条件の実挙動。年齢の選択肢範囲（§B-8-1）もここで確定できる。
- 理由: 入室前画面の表示自体は入室操作に直結し、今回の許可範囲（影響操作なし）では開かなかった。docs は2026-10-04採取に基づく。
- 手順: (1) 実機で待機中の部屋を1件タップし、入室前画面の項目・文面をアプリ表示と比較。(2) 同じ相手の部屋で時間を置いて再表示し、一時IDが変わるか記録（値は外部に出さない）。(3) 年齢欄がセレクトなら上限を確認。

## C-2. 作成者側 ajax.php 応答の採取（#31）
- 未確認: 自分の部屋に相手が入室（aj_alert_in）、相手退室（aj_guest_off）、部屋終了（die_msg）の実応答形式。アプリの解析は入室者側の採取形式からの類推を含む。
- 理由: 2端末での実チャットが必要で、本監査の範囲外。
- 手順: 自分の端末で部屋を作成し、家族・知人の端末（または自分の別端末）から入室→発言→退室を実施。Mac の Chrome DevTools で `ajax.php` 応答を HAR 保存し、名前・pwd を伏せて開発側へ共有。

## F-10 は ChatGPT の見立てより重い（Claude の指摘を採用）

- ChatGPT は「行欠落が部屋消失の誤認材料になる」までだったが、実際には `RoomPageWindow` の閉鎖推定が能動的に誤判定する。読んだページの ID 範囲内にあるのに載っていない部屋は「閉じた」として一覧から外され（`RoomPageWindow.kt:44-46` の closedRange と gone 判定。コメントにも「このページの範囲にあるのに載っていない部屋は閉じた」と明記）、持ち越し部屋も closedByRun で落とされる。
- パーサの「読めた」判定は欠落行を数えないため、1行落ちたページも完全な観測としてこの推定に使われる。ピン側では不在が閉鎖判定の材料になる。

## F-08 への Claude の反論は一覧系については正しい（ただしチャットはゲート外）

- Claude の「自動の通信はすべて ShaloveClient の1本のゲートを通るので頻度の上限は守られている」は、一覧取得・入室・作成者操作・公開ルーム取得についてはコードどおり（一覧系は `gated()` の単一 Mutex と最小間隔で律速される）。機能ごとに再試行時計が分かれていても、合算の頻度が上限を超えるわけではない。ChatGPT の F-08 はこの点で過大評価である。
- ただし厳密には、チャットの ajax（`ChatSession` の poll と発言）は ShaloveClient のゲートを通らず、専用の OkHttp で直接通信する（`ChatSession.kt:107,145`）。こちらは PollSchedule と live=1 のロングポーリング、発言1.5秒間隔で独自に律速されており、実害の形は異なる。結論として F-08 は「共通停止と Retry-After が無い」という設計論点のみが残り、重要度は ChatGPT の P1相当から中へ下げるのが妥当である。
