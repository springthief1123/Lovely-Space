# オンデバイスAI 第5段階 — 取得済みの公開募集文をdebugで手動検索

管理: [Issue #112](https://github.com/springthief1123/Lovely-Space/issues/112)。既存の未マージDraft PR #105→#107→#109→#111 を土台にした後続実装。**実サイトへの新規アクセス・本番検索UIの変更・自動通知は実装しない。**

## 目的・本番統合との違い

Galaxy Z Fold5でCPU推論・100件の検索・文書キャッシュ復元・モデル解放・通常画面の操作を検証した。次は、架空の文書から一段進めて、**すでにLovely Spaceが取得した公開待機中の部屋一覧だけ**を明示的に手動検索できるかを試す。debug APKの **「プロフィール → 設定 → 開発者用ツール」** に「取得済み一覧AI検証」を設け、本番ユーザーの「見つける」やレーダーには接続しない。ホームのアイコンは通常のLovely Spaceだけ。

既存のSite通信を新たに実行しないよう、唯一の入力は`(application as LovelySpaceApp).roomLists.observations.value`。HTTP `fetch`や画面リロードは呼ばない。取得済みページがなければ何も推論せず、**利用者が自分で通常の「見つける」を開く**案内だけを表示する。

## 端末内データ保護

- ユーザーが「取得済み一覧を端末内で意味検索」を押した場合に限り、既存スナップショットを読み直す。**初期状態でAIを自動実行しない**。
- 対象は直近10分以内の取得済みページ、待機中の部屋（満室は除外）、募集文が空でないもの。部屋ID・ジャンルはメモリ上の重複除外にだけ使い、モデル入力に入れない。名前・性別・年齢・地域・識別子・`pwd`・Cookie・チャット本文もモデル入力に入れない。
- **募集文は1件最大240文字、計100件、希望文最大120文字**。表示と推論のためのメモリ内の文字列だけを使用する。推論SDKはLiteRT-LM CPUで端末内で動作し、モデルはアプリ内に取り込み済みのファイルを使う。
- デバッグPoCの合成文専用`PocVectorCache`にも実サイトのデータを入れない。**永続ベクトルファイル・パフォーマンスCSV・品質CSV・Androidログ・GitHubには何も書き込まない**。画面上には募集文が表示されるが、端末外へ自動送信しない。ユーザーが画面を離れた場合はActivityを終了して一時結果を破棄し、モデルも解放する。
- 募集文に連絡先などが含まれている可能性は残るため、**実サイトの文面を画面撮影して公開しない**。この段階で取得した実部屋の文章・順位をGitHub Issue/PRへ貼らない。結果を報告するときは件数・所要時間・動作成否などの数値だけを共有する。
- 実データを扱う独立debug画面から通常のアプリロックを迂回しないよう、**アプリロックが有効な場合は検証画面で一覧を読まず検索も実行しない**。解除済みであっても、ロック機能が有効な間は検証不可とする。端末の`FLAG_SECURE`で画面のスクリーンショット／最近使ったアプリのプレビューも防ぐ。通常のLovely Spaceのロック設定は変更しない。
- リリース版にはこの検証Activity・SDKを同梱しない。設定内の開発者用ツール入口も表示せず、画面本体にはrelease向けの空実装を用いる。将来実データのベクトルを永続化する場合は、別途プライバシー・規約と保持期限を検討する。

## Galaxy Z Fold5での手動検証

1. CI成功した第5段階のdebug APKを**上書き**インストールし、必要なら **プロフィール → 設定 → 開発者用ツール → AI意味検索検証** でモデル`embeddinggemma-2-text-270m.litertlm`を取り込む。
2. 通常のLovely Spaceで「見つける」に表示される一覧を待つ。新しいテストのためにサイトを必要以上に更新しない。**アプリを強制停止せず**、同じアプリ内のプロフィールから設定へ進む。
3. **設定 → 開発者用ツール → 取得済み一覧AI検証** をタップし、「取得済み一覧の件数を再確認」を押す。直近10分以内に取得済みの待機中募集文がなければ0件と表示される。0件では推論できず、通信も行わない。
4. 日本語で短い希望文を入力し、**明示的に一度だけ**「取得済み一覧を端末内で意味検索」を押す。件数・モデル初期化・埋め込み・総時間と上位10件の募集文・類似度が表示される。
5. 順位の納得感や所要時間を端末上で確認する。**実サイト由来の文面やスクリーンショットをGitHubへ投稿しない**。このチャットへの報告は「何件・約何秒・並び方は自然か」などで十分。
6. 機内モードでも、**すでに取得された一覧がプロセス内に残っている限り**同じ操作ができるか確認する（通常画面のリロードを行わない）。アプリ強制停止後は観測スナップショットが失われるので0件になり、これは仕様。
7. 検証画面を離れて戻ると結果が破棄され、モデルは解放される。リリース版の検索・通知動作は変更されていない。

## 受け入れ条件・未確認事項

- コード・ユニットテスト・LintはGitHub Actionsで検証する。**Galaxy Z Fold5での手動検索はCIだけでは確認できない**。
- この手動PoCからは、既存の検索条件が守られるか、実際の検索結果が本番で正しく統合できるかを自動保証しない。実サイトのデータ利用に関する規約・プライバシー、ユーザーによる明示同意、ベクトルの安全な破棄・期限、自動再取得を行わない保証を本番機能として再設計する必要がある。
- コサイン類似度は相対値であり確率ではない。自動通知やチャット入室のトリガーには使用しない。
- Kotlin 2.1/2.4とLiteRT-LMの互換回避はdebug専用のまま。本番導入には別Issueでツールチェーン・モデル配布・ライセンスを設計する。

## 開発者用ツールへの集約（2026-10-11）

利用者から「3つのホームアイコンを使い分けるより、設定画面の開発者用ツールへまとめるべきではないか」と提案があった。この設計を採用し、過去のタスク分離方式は撤回した。

| 入口 | 遷移先 | 内容 |
| --- | --- | --- |
| ホームの唯一のアイコン「Lovely Space」 | `MainActivity` | 通常のアプリ |
| プロフィール → 設定 → 開発者用ツール | アプリ内の開発者用メニュー | debugビルドだけに表示 |
| 開発者用ツール → AI意味検索検証 | `EmbeddingPocActivity` | モデル取り込み・合成文・品質/性能/メモリ検証 |
| 開発者用ツール → 取得済み一覧AI検証 | `ExistingSnapshotSearchActivity` | 取得済み公開募集文だけの手動検索 |

- debug Manifestから2つの検証Activityの`MAIN/LAUNCHER`と個別の`taskAffinity`を削除し、`android:exported=false`へ変更。外部アプリから検証画面を直接起動できない。
- メニューと検証画面はアプリ内の同じタスク・プロセスで動くため、通常の「見つける」が保持する`roomLists.observations`が共有できる。
- `src/debug`と`src/release`にビルドごとの`DeveloperTools`実装を用意し、リリース版では入口を表示せず、実装も含めない。
- Android単体テストで`MAIN/LAUNCHER`が`MainActivity`1件だけで、検証Activityが外部非公開であることを確認する。
- 古いAPKから変更した場合、**上書きインストール**後に古い「最近使ったアプリ」のタスクを閉じる（必要ならアプリを強制停止）。モデルファイルを守るため、**アンインストールやデータ消去をしない**。取得済み一覧はその後通常画面で読み込めばよい。
- Galaxy Z Fold5で **設定 → 開発者用ツール → 2種類の検証画面 → 戻る** の動作とモデルファイルの残存を確認する。ロック有効時の「取得済み一覧AI検証」は従来どおり制限される。

## 実データ検索品質の再検証（2026-10-14 / Draft改善PR）

Galaxy Z Fold5で短語・自然文のどちらでも関連性の弱い募集文が高スコアで上位に現れたため、**推論の成功と検索品質の合格を分離**して調査する。今回の改善もdebug専用で、本番の「見つける」／通知／巡回／追加通信／Room DBは変更しない。

### 新しい検証UI

1. 「見つける」で必要なカテゴリーを通常どおり表示したあと、**強制停止せず**「プロフィール → 設定 → 開発者用ツール → 取得済み一覧AI検証」へ進む。
2. 「対象カテゴリーを選択」で取得済みカテゴリーを1つ選ぶ。直近10分以内に募集文のあるカテゴリーだけが選べ、ほかのカテゴリーの観測は検索対象に含めない。最大100件、募集文240文字、希望文120文字の既存上限を守る。
3. 「希望する雰囲気」に日本語を入力する。短い語句の検証では「文字列照合の語句」を必要に応じて入力する。**照合語句が空欄のときに限り、希望文が12文字以下・空白なしなら同じ文字列で照合する**。長い自然文では自動抽出しない。
4. 手動検索結果を比較する。「文字列一致した募集文」はNFKC正規化・大文字小文字非区別の**募集文の部分一致**であり、AIのスコア順で表示する。一致ゼロなら**明確に一致ゼロ**と表示する。「文字列不一致のAI候補」は関連性未確認の参考枠（最大5件）であり、確定一致に混ぜない。
5. 「AI上位10件の文字列一致件数」「類似度の最大／最小」「対象件数」「所要時間」を確認する。数値は順位の問題を切り分ける参考情報であって、スコアが高いことは適合の保証ではない。

**注意点**：カテゴリー選択は既存観測の絞り込みのみ。部屋の名前・タイトル・年齢・地域・IDは依然としてモデルと文字列照合に渡さない。「チャH」と「ちゃえっち」など**意味上の同義語は文字列一致に含まれない**。表記差についてはNFKC（例: 半角カナ）のみ吸収する。複数キーワード・AND/OR、意味閾値、通知連携を導入したわけではない。

### 受け入れと安全条件

- 合成文の単体テストで、カテゴリー隔離・古い観測／異常ジャンルの除外・半角カナの正規化・短文／自然文の扱い・高スコア無関係候補の分離・該当なし判定を確認する。
- 実機では、**同一カテゴリー・同程度の取得件数**で短語と自然文を比較する。文字列一致件数、AI上位10件中の一致件数、所要時間、関連性の主観的傾向だけを報告する。実際の募集文、個人名、部屋ID、スクリーンショット、生CSVをGitHubへ出さない。
- 入力・推論結果は画面のメモリだけ。追加HTTP要求や外部AI API、実文面の永続キャッシュ／ログ／CSV保存は行わない。ロック有効時の拒否と `FLAG_SECURE` を維持。モデルは使用後に解放する。
- **検索品質そのものは未検証**。モデル入力の互換性、異なる語彙の想起、同義語扱い、正解ラベルつき適合率、長時間安定性は別途実機評価が必要。改善を採用判断に使うのは実機検証後とする。
