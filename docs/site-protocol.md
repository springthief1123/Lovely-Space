## 部屋一覧の行（`table.rooms` > `tr.roomcol`）

広告を挟んで `table.rooms` が複数に分割される。行は 6 列:

1. **利用状況**: `td.wait` / `td.fill`。`span` 内が `待機中` / `公開待機中` / `満室`。`font.room_time` に経過時間 `HH:MM:SS`
2. **入室**: GET フォーム。`room_id`（数値）と `genre_key` を hidden で持つ
   - 待機中 → `action=/PreEnterRoom`、ボタン `入室`
   - 満室・公開 → `action=/PublicRoom`、ボタン `覗く`（観覧）
   - 満室・非公開 → `/PreEnterRoom`、ボタン `秘密`（disabled）
3. **名前**（満室時は `span.heartmark` 「2ショットチャット中」に置き換わる）
4. **性**: `span.male` / `span.female`（満室時は `span.hearttext`）
5. **年**: 数値または `&nbsp;`
6. **メッセージ**: 先頭に地域タグ `<font class="small" color="#339933">大阪</font>` が付くことがある。満室時は広告リンクが表示され、本来の募集文は `span.hearttext[style=display:none]` に隠れている

→ `room_id` は数値 ID だが、**サブドメイン（host）ごとの値で、部屋が閉じた後に別の部屋で再利用されることがある**。ブックマーク・順番待ちのキーは `host + room_id` にし、使う前に一覧で見える名前・性別・年齢が登録時と一致するかを照合し直す（app の `RoomPreference`、core の `RoomIdentityEvidence.REUSED` が実装例）。

## サイト側の絞り込み（GET パラメータ）

`/g/<genre>/?vsex=&vpref=&vyears=&vnonpub=&vwait=&srchname=&srchmsg=`

| パラメータ | 値 |
|---|---|
| vsex | 1=男性, 2=女性 |
| vpref | 1〜47 都道府県, 48=海外 |
| vyears | -19, 20-29, 30-39, 40-49, 50-59, 60- |
| vnonpub | 1=非公開, 2=公開 |
| vwait | 1=待機中, 2=満室 |
| srchname / srchmsg | 名前・メッセージの部分一致（単語1つ） |

→ アプリの高度な検索は「サイト側パラメータで一次絞り込み → 端末側で AND/OR・除外ワード・並び替え」の二段構えにすると取得量を減らせる。

2026-10-09〜10-16 のアプリは、この二段構えで性別・待機・公開・年齢帯と語（`srchname` / `srchmsg` に 1 語）を本家に渡していた。本家は大文字・小文字も かな/カナ も区別する（Chrome 拡張の記録）ので、英字を含む語・Shift_JIS で表せない語は渡さず、かなを含む語はひらがな・カタカナの書き方ごとの一覧を取って合わせていた。

2026-10-16 から（Yuya の決定）、見つける画面とレーダーは**本家側の絞り込みを使わず**、ジャンル全体の一覧（`/g/<genre>/` と `/pageID/`）だけを読む。条件はすべて端末で判定する（`RoomSearchCriteria.matches`。全角・半角、大文字・小文字、ひらがな・カタカナ、長音・波線の揺れと言い換えを `KeywordFolding`・`SynonymDictionary` で吸収）。語を変えるたびに本家の一覧を 1 ページ目から取り直すと、ページ数 × 最小間隔だけ結果が遅れるため。Chrome 拡張も既定では語を本家に渡さず（`pushTextSearch: false`）、取得済みの一覧を手元で絞り直している。代わりに大きいジャンルでは読むページが増える（関東は 1000 部屋超で、1 ページ 60 件なら十数ページ）。

## アクセス頻度の制限

- 2026-10-08、Yuya がブラウザで一覧の更新ボタンを 1 秒に 5 回以上の頻度で押し続けたところ、サーバーの負荷を理由に一時的にアクセスを禁止された（画面の文言・禁止の長さ・HTTP ステータスは未採取）。どの頻度から止められるかは分かっていない。
- アプリが自動で行う通信は、リクエスト同士の間隔を 1 秒より短くしない（`RefreshPacing.FLOOR_MIN_INTERVAL_MS`）。自動の通信は毎分 60 回が上限で、止められた頻度の 5 分の 1 以下。利用者が押した取り直しは次の項目のとおり。
- 一覧の上部の「最新更新」（`<a href="index.html" class="pagereload">`）は 1 ページ目を読み直すだけのリンク。アプリの見つける画面の更新ボタン・引っ張って更新も同じく 1 ページ目を取り直し、読み込み中でも押すたびに取り直す。本家では押す間隔に制限が無いので、アプリも前の通信から間隔を空けない（2026-10-17、Yuya の決定。通信は 1 本ずつで、取り直し中の連打は 1 回にまとめる）。
- 更新ボタンを続けて押したとき、本家が部屋の表（`table.rooms`）だけが無い一覧ページを 200 で返すことがある（2026-10-17、Yuya の実機で全国・チャH とも観測）。題名・見出しの「待機中」「満室」の数はふだんどおりで、本文は 2.5〜3 万文字と、表がある時の半分ほど。表の代わりに何が出ているかは未採取。アプリはこれを 0 件の一覧として取り込まず（`RoomListParser.isReadable`、`RoomListUnavailableException`）、見つける画面では案内も出さずに手元の一覧のまま次の取り直しを待つ（ブラウザで押し直すのと同じ扱い）。見出しも行も無いページも同じく取り込まない。2 ページ目以降も、見出しの部屋数が前のページまでに収まらないのに行が無ければ同じく取り込まない（以前は 2 ページ目以降の空のページをそのまま取り込み、そのページの部屋を消えたことにしていた）。

## 文字コード・JS

- サイト自身の JS (`/js/common.js`, `/js/genre.js`) は Shift_JIS。HTML も Shift_JIS と推定（取得ツールが UTF-8 に変換して保存しているため未確定）
- 一覧ページに自動更新（meta refresh / タイマー）は見当たらない。「自動更新」はチャット画面側の機能と思われる
- 一覧は **1 ページ 60 部屋**でページ分割される: `/g/<genre>/pageID/<n>/`（関東は 18 ページ、`待機中 1005 / 満室 57`）。ページャは `<p align="center">` 内の `<a title="… 次のページ">`
- 一覧は部屋を立てた時刻の新しい順で、部屋の ID（本家全体の通し番号）の大きい順と一致する。2026-10-04 の採取（9 ジャンルの 1 ページ目）で、順が逆になるのは同じ秒に立った部屋同士だけ（ID の差は 3 以内）。満室の部屋も同じ位置に並ぶ。アプリは読んだページの ID の範囲（端から `RoomPageWindow.ID_MARGIN` を除く）にあるのに載っていない部屋を、閉じた部屋として一覧からすぐ外す（ID は閉じた後に使い回されることがあるので、ページの中で ID の順が崩れていれば範囲を使わず、いちばん大きい・小さい ID も範囲の端にしない）。取り直したページから消えた部屋は、後ろのページは周に 1 つしか読まないので何ページもずれていることがある。アプリは閉じたと分かるまで（消えた後に続けて読んだページの並びの間に入るのに無いとき）一覧に残し、ページの末尾ではなく立てた順の位置に並べる（使い回しの ID の部屋は並んだ位置で数える。`sortKeys`）。同じ人が部屋を閉じて同じ名前・募集文で作り直す「立て直し」では ID が新しくなる。アプリは閉じたと分かった部屋と名前・募集文（表記の揺れをそろえる）・性別・年齢が一致する新しい部屋がちょうど 1 つあれば立て直しとみなし、順番待ち・追跡・保存・非表示を新しい部屋へ移す（`RoomPageWindow.rebuildOf`。満室で名前が出ない部屋は 10 文字以上の募集文だけで照合する）。立て直しの新しい部屋は 1 ページ目に出るが、古い部屋が後ろのページに載っていると、そのページを読み直すまで新旧が一覧に並んでしまう（後ろのページは周に 1 つずつ読むため。2026-11-05 Yuya 報告）。そこで古い部屋の載るページを最後に読んだ後に立て直しの部屋が初めて見えたら、古い部屋を画面の一覧から外す（`RoomPageWindow.superseded`。閉じたとは決めないので、ピン・順番待ちはページを読み直して確かめてから移る）。読み直して古い部屋がまだあれば、同じ人が 2 部屋立てているので本家と同じく両方出す
- 絞り込み中（PC 版レイアウト）は 1 ページ目が `/g/<genre>/?vsex=1`（本家の絞り込みフォーム `#shibori` の GET）、2 ページ目以降は**条件がパスに入る**: `/g/hokkaido/vsex/1/pageID/2/`。ページャには全ページへのリンクが並ぶ。複数の条件を組み合わせたときのパスの並び順は未確認なので、アプリは一覧に載っていたページャのリンクを優先して使う（`ShaloveClient.fetchRoomList`）
- 別の形の一覧 `/?action=GenreK&genre_key=..&vsex=..&vpref=..&vyears=..&vnonpub=..&vwait=..&srchname=..&srchmsg=` もある（`<hr>` 区切りの軽いレイアウト、`table.rooms` ではない）。ページ送りは `pagernext` の `&bfrid=<room_id>` カーソルで、件数は `22-25/25部屋` の形。2026-10-09 の採取で、関東・女性・待機中は 25〜26 部屋、`vsex`・`vwait` は 2 ページ目でも保たれることを確認した。1 ページの件数は一定でない（21 件・26 件・60 件を観測）。アプリはこの形を使わず PC 版の `/g/` を使う
- 本家側で絞ると取得量が大きく減る（関東 1000 部屋超 → 女性 67 部屋 → 女性・待機中 25 部屋前後）

### 1. 行と各項目の位置

部屋ごとのコンテナはなく、同じ親の兄弟ノードを `hr` で区切る。見出しにも「満室」の `font` があるので、文言だけで部屋に数えず、絞り込みフォーム・ページャ等を除く必要がある。

| 状態 | 行の先頭・リンク | 名前・年齢・性別・地域・募集文 |
| --- | --- | --- |
| 待機中（非公開） | `a[href]` の文字が `待機中`、パス `/PreEnterRoom` | リンク直後のテキストが `名前(年齢)`、その次の `font.male` / `font.female` が性別。性別 `font` の後のテキストが地域、`br` の後の `span.wrapsoft` が募集文 |
| 公開待機中 | 同じ構造でリンク文字が `公開待機中` | 同上 |
| 満室の公開 | `font[color="#ff00cc"]` の文字が `満室`、続く `a[href]` が `覗く`、パス `/PublicRoom` | 覗くリンク直後に部屋主名。年齢があれば末尾の括弧内。性別・地域・募集文は待機中と同じ位置。PC 版のように名前を「2ショットチャット中」に置き換えない |
| 満室の非公開 | `font[color="#ff00cc"]` の `満室` と、その後のテキスト `非公開` | 名前・年齢・性別・地域・募集文・入室／覗くリンクは無い。新形式ではさらに時間の `span.listbtime` がある |

- 男性は `font.male[color="#0000ff"]`、女性は `font.female[color="#ff0000"]`。名前には専用要素・属性が無い。名前自体にも括弧があり得るので、年齢を切り出すなら**末尾の数字の括弧だけ**を見る。年齢・地域は任意で、省略を欠損と決めつけない。
- 新形式の地域の後（地域が無ければ性別の後）、`br` の前に `span.listbtime`。地域を読む範囲に時間を混ぜない。旧 adapter の「性別の後から br まで」という前提だけでは、時間を地域に混ぜるおそれがある。
- `/PreEnterRoom` の `href` の query に `room_id`, `genre_key`, `kct`, `back_uri`。`/PublicRoom` は `room_id`, `genre_key`, `back_uri`、新形式の今回の行にはさらに `pre` があった（旧形式には無かった）。リンク先には移動していないので `pre` の意味は未確認。
- `room_id` はリンクから取得できる行だけにある。`kct`・`back_uri`・`pre` を識別キーに使わない。リンクを再構築して入室できるかの検証は本調査の対象外。
- 両形式の今回の HTML の meta は `text/html; charset=UTF-8`。HTTP Content-Type は `text/html` で charset 指定なし。PC 版の過去の文字コード推定を流用しない。

### 2. 「◯分◯秒前」と PC 版の時間

新形式は**応答 HTML に `span.listbtime` のテキストとして時間が既にある**。21 行すべて（満室公開 3 行・満室非公開 1 行を含む）に存在し、UTF-8 の文字列が生の応答内にあることも確認した。行内の時間要素には `class` 以外の属性が無く、時刻・秒数・`data-*`・`datetime`・`title` は無い。行のほかの要素にも元の時刻を示す属性は見つからない。入室リンクの `kct` は旧 adapter でも取得時のトークンとされており、部屋を立てた時刻と解釈しない。

| 新形式で観測した表示 | 同じ部屋の PC 版 `font.room_time`（約 29 秒後） | 読み取り |
| --- | --- | --- |
| `37秒前` | `00:01:06` | 秒までの表示では取得時刻の差と一致 |
| `2分48秒前` | `00:03:17` | 同上 |
| 満室公開の `6分前` | `00:06:45` | 約 29 秒を戻すと 6 分台 |
| 満室公開の `8分前` | `00:08:50` | 同じく 8 分台 |

観測範囲では 3 分未満は秒まで、3 分台からは `3分前` のように秒を省いた（正確な切り替え境界そのものは未確認）。最大は `13分前`。満室公開でも PC 版の経過時間と矛盾しない。**部屋作成からの経過時間と考えるのが自然だが推測**であり、満室になる瞬間や相手退室の前後を観測していないため、「会話開始時にリセットしない」とまでは確定していない。

## サイト側の既存機能（アプリとの重複に注意）

- 公開ルーム = 登録不要・覗き可能・出会い目的禁止。非公開ルーム = 会員＋年齢確認（証明画像提出）が必要。「通話」など非公開専用ジャンルもある

### 新着取得と発言（`/js/2shot.js`）

- `GET ajax.php?live=1&room_id=..&pwd=..&fromsize=<N>&kct=<ms>` で新着を取得。`live=1` は「常時自動更新」（長めに接続を保つ方式の可能性。要確認）

- **レスポンスは JavaScript 文字列**で、ページ側が `eval` する。設定される変数:

- 発言: `POST ajax.php?&room_id=..&pwd=..&fromsize=<現在値>&kct=<ms>`、本文 `chat=<UTF-8 URL エンコード>`。応答は自分の発言を含む新着（即時、46ms）

| 非公開に変更 | `set_is_public=0`（参加者が年齢確認済みの場合のみ） |
| 待機メッセージ変更 | `chat=` 空 + `message` |
| ROM 表示切替 | GET `not_show_rom=0/1` |
| 画像投稿 | `POST https://chat.shalove.net/?action=Distributed_LocationImgUp`（multipart, `upfile`, `return_host`）。メール `<pwd>@img.shalove.net` 宛添付でも可 |
| ログ全文 | GET `/RoomLog?room_id=..&pwd=..` |

- `2shot.php` は `charset=UTF-8` のページで、フォームも UTF-8 で送られる（入室前画面の名前も UTF-8 で送信されていた）。
- フォームは JS で横取りされず、普通に送信されて部屋の画面が再表示される。アプリは応答が部屋の画面なら読み直し、公開設定・待機メッセージ・「相手を退室」の有無を確かめる（`ShaloveClient.banGuest` など）。
- 「相手を退室」（`form#form_ban`）は相手がいないあいだ `display:none` で置かれている。`2shot.js` は新着取得の応答で `aj_alert_in`（入室者あり）なら表示し、`aj_guest_off` のときは `aj_can_ban_guest` に従って表示・非表示を切り替える。
- 発言クリアのフォームは `form#form_clear`。`2shot.js` には `ajax.php?…&shotact=clearchatlog` で送る経路もあるが、採取したページからは呼ばれていない。
- 非公開の部屋で「公開に変更」（`set_is_public=1` と推定）が出るかは未確認。アプリは `set_is_public` の入力欄があるときだけ切り替えを出す。

### 入室通知（Web プッシュ）

- `webpush.js`: Service Worker `/sw.js` を登録し、購読情報（endpoint, p256dh, auth）を `GET /Jsapi_SubscribeWebPush?endpoint=..&publicKey=..&authToken=..&room_id=..&pwd=..` で登録。会員は `/Ipush_SetQuick` もある
- VAPID 公開鍵はページ内に固定値で記載
- **アプリへの応用案**: Android アプリでも UnifiedPush（ntfy など）を使えば標準の Web プッシュを受け取れる。購読情報をこの API に渡せば、**アプリがポーリングせずにサーバー側から入室通知を受け取れる**可能性がある（サイト公式機能の利用なので規約面でも有利）。実現性は要検証
