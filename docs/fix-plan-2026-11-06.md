### T1. F-10 一覧の部分解析欠落対策

- 現象: パーサが落とした行の部屋が、`RoomPageWindow` の閉鎖推定（読んだページの ID 範囲内に無い部屋は閉じた）で能動的に閉鎖扱いされ、一覧から消え、ピンでは閉鎖と誤判定される。
- 変更内容:
1. `core/RoomListParser.kt`: ページ内の部屋行候補数（解析対象の行数）と解析成功数を数え、`RoomListPage` に「完全かどうか」（例: `droppedRowCount` または `rowsComplete`）を持たせる。候補の数え方は現在の行特定方法（PC版 table / hearttext）に合わせ、広告行など正当な非部屋行を候補に含めない。
2. `core/RoomPageWindow.kt`: 完全でないページの観測では、ID 範囲による閉鎖推定（closedRange / closedByRun）を適用しない。そのページに載っている部屋の更新自体は通常どおり取り込む。
3. 観測の完全性を使う側（`RadarRepository` の observe 経路、`RoomObservationJournal` の completePageIds 相当）でも、不完全なページを「完全な観測」として扱わない。
- 変更しないこと: 1件も読めないページの扱い（既存の isReadable）、並び順・sortKeys、ピン側の判定条件そのもの。
- テスト: 合成 HTML で「中ほどの1行だけ列数が崩れたページ」を作り、(a) その部屋が一覧から消えない、(b) 本当に閉じた部屋は従来どおり消える、(c) ピンが閉鎖にならない、を RoomListParserTest / RoomPageWindow のテストに追加。
- 受け入れ条件: 上記テストと既存テスト全件が CI で成功。

### T2. F-07 チャット応答の妥当性判定

- 現象: 代入文が1つも無い 200 応答（認証画面・メンテナンス・空本文）でも `ChatUpdateParser` が前回状態の複写を返し、`ChatController` が失敗回数をリセットして「接続中」になる。送信応答でも成功扱いになり得る。
- 変更内容:
1. `core/chat/ChatParsers.kt`（ChatUpdateParser）: 応答に `gRoomVars.fromsize` の代入も `die_msg` も無い場合は「チャット応答ではない」として失敗を返す（parse の戻り値で失敗を表すか、専用の例外にするかは既存の呼び出し側の形に合わせる）。
2. `core/chat/ChatSession.kt`: poll で上記失敗を受けた場合は通常の通信失敗と同じ経路（例外として伝播）にする。state（fromSize 等）を進めない。
3. 送信（postAjax の応答）で同じ失敗になった場合は「送信できたか不明」の状態を UI に出し、自動での再 POST はしない（`app/.../ChatController.kt` の送信結果の扱い）。
4. `ChatController` の失敗回数リセットは「妥当な応答を受けたとき」だけにする。
- 注意: 本家の正常応答には採取記録上必ず fromsize が含まれる。die_msg のみの終了応答を弾かないことが必須条件で、終了応答の合成 fixture で回帰テストする。#31 の実応答採取が済んだら fixture を差し替える。
- テスト: 空本文、認証 HTML、die_msg のみ、正常な空ログ（loglines が空配列だが fromsize あり）の4ケースを ChatParsersTest / ChatClientTest に追加。

### T3. F-08 残論点: 制限応答への共通停止

- 現象: 403/429 等への共通クールダウンが無く、Retry-After を読んでいない。機能ごとの再試行が別々に走る（一覧系の合算頻度は単一ゲートで律速済みなので、頻度そのものではなく「制限に気づいて全体で止まる」仕組みの欠如が対象）。
- 変更内容:
1. `core/ShaloveClient.kt`: 応答の保持（Fetched）にステータスだけでなく Retry-After ヘッダも含める。403/429/503 を受けたらホスト単位の共通停止時刻を記録し、`gated()` は自動系（operation=false）の取得を停止時刻まで待機または失敗させる。利用者の明示操作（operation=true）は止めない。
2. チャットの ajax はゲート外だが、停止中は `ChatSession` の poll も同じ停止状態を参照して休止する（PollSchedule 側で確認する形でもよい）。
3. 自動入室（AutoEntry）は停止中は試行しない。
4. 200 の制限・警告ページの検出は、本家の実例が未採取のため今回は入れない（採取できたら別タスク）。
- テスト: MockWebServer で 429＋Retry-After を返し、検索相当・ピン相当の自動取得が停止し、手動操作は通ることを ShaloveClientTest に追加。
- 受け入れ条件: 制限応答1回で全自動機能が止まり、停止が明示操作を妨げない。

### T4. F-06 背景監視の登録条件にピンを含める

- 前提: T0 で #186 がマージ済みであること。
- 変更内容:
1. `app/LovelySpaceApp.kt`: 背景スケジュール登録の combine 入力にピンの監視需要を加える。需要の定義は「未配信の空きイベントがあるピン」「満室・空き・閉鎖のいずれかで、次に状態変化を見張る価値があるピン」とし、ピン0件では登録しない。
2. `app/background/BackgroundSync.kt`: 1回3ページの枠に、対象ピンのページに加えて閉鎖ピンのジャンル1ページ目（立て直し検出用）を公平に割り当てる。
3. `Waitlist.hasPendingWork` 周辺の数え方にピンを含めるか、ピン需要を別入力として合成する（実装時に既存構造へ薄く足す）。
- 変更しないこと: 周期の最短15分、Foreground Service の新設（#153 の範囲）、即時性の改善。
- テスト: ピンの内訳（空きのみ／閉鎖のみ／満室あり／0件）ごとに登録・解除が切り替わるユニットテスト。実機では監査 §C-06 の手順で登録有無を確認。

### T5. F-01 作成画面の公開範囲の注記と email 欄

- 変更内容（段階1・依存なし）:

- テスト: prefill に email が含まれること、注記が表示されることの ViewModel / 画面テスト。実機では監査 §C-10 の手順で未ログイン／ログイン／年齢確認済みの3条件を確認。

### T6. F-12 WebView のファイル選択対応

### T7. F-09 WebView 引継ぎの用途別検証（#124 C-48）

- 変更内容: `SiteWebView.kt` の `toChatRoom` とフォーム解析の引継ぎに、呼び出し側から期待するホスト（と入室時は元の room_id）を渡して検証する。用途別の扱い:
- 入室: 元の部屋のホスト・ID と一致する場合だけネイティブへ引き継ぐ。
- 作成: 対象ジャンルのホスト配下であれば受理（新規 ID のため ID は問わない）。
- 再入室: 本家の転送でホストが変わる実例があるため、ジャンル整合が取れる場合に限り受理し、それ以外は本家画面のままにする。
- あわせて、引継ぎで旧接続を閉じる際の扱いは現行の保護（新規接続開始時のみ旧を閉じる）を維持する。
- テスト: 合成 URL で別ホスト・別 ID を拒否し、正しい遷移を通すケースを SiteWebView 周辺のテストに追加。
