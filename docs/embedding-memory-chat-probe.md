# オンデバイスAI PoC 第4段階 — モデル解放と通常チャット画面のRAM/CPU計測

> 管理: [Issue #110](https://github.com/springthief1123/Lovely-Space/issues/110) / Draft PRは本実装の作業ブランチ。元のPoC: #105 → #107 → #109。本機能は **debug専用**であり、実際のサイトの取得や通知をAIに接続しない。

## 背景

Galaxy Z Fold5でEmbeddingGemma 2 Text 270MのCPU推論と日本語意味検索を確認済み。100件合成文の全件新規計算は約8.7秒、モデルと文書ベクトル両方を保持すると約166ms、アプリ強制停止・再起動後にディスクベクトル100件を復元した場合は約654ms。これまでの測定ではPSSの観測ピーク約400〜430MiBだったが、**モデルを解放した後にどこまでメモリが減るか**、**通常のチャット画面での同一プロセスのRAM/CPU負荷**が不明だった。

今回の狙いは、利用者が自分の端末で検証ログを安全に取得すること。**AIと実チャットの同時推論を本番へ入れる試験ではない**。PoCをバックグラウンドで推論させず、本番の巡回・通知・チャット通信コードは変更しない。

## UIと2種類の検証

### A. モデル解放後のRAM変化

1. 最新のPRに付属するdebug APKをGalaxy Z Fold5へ導入する。ホーム画面の「AI意味検索検証」を起動する。モデルファイルは同じアプリIDなので通常は既存コピーが使用可能。
2. 「画面内でCPUモデルを一時再利用する」= **ON**、「永続ベクトルキャッシュ」= 任意。まず5件か100件の意味検索を1回実行し、モデルをメモリに保持する。
3. 画面内の「読み込み済みモデルを解放してRAMを測る」を押す。**操作してから3秒間は画面を離れない**。
4. 解放前、直後、250ms、1秒、3秒の5回のPSS、Native PSS、Java/Native heap、プロセスCPU時間、バッテリー温度等を数値ログに記録する。画面にはPSSの前→3秒後、モデル保持が消えたかを表示する。
5. 「読み込み済みモデルを解放する」の従来ボタンや、アプリの背面化でもモデルは解放するが、それらは今回の**明示的な5点計測**とは別。背面化後の状態は次のBで観察する。

**注記：** PSSの差が直後に出ない場合でもモデル解放の失敗とは限らない。ネイティブメモリの回収・Androidのページ解放・GCのタイミングはOS次第。モデル解放確認には`engine_loaded=false`を併せて使う。`engine_loaded=false`はSDK側のオブジェクト参照の解放状態であり、ネイティブメモリ全量が回収された保証ではない。

### B. 通常のLovely Space画面の負荷

1. 「AI意味検索検証」でモデル再利用ONのまま一度意味検索して、モデルを保持した状態にしておく。
2. 「負荷計測を開始して通常のLovely Spaceを開く」を押す。**通常のMainActivityが起動**する。PoC画面が背面に移ると、既存の`onStop`がモデルの解放を要求する。
3. 通常のLovely Space内で、**自分の普段の使い方**（画面移動や、任意で既存のチャットを開くなど）を最大90秒操作する。チャットの入力内容や入室情報を検証のために共有する必要はない。**テストのために余分な巡回や入室を行う必要もない。**
4. 端末のホーム画面等へ移って5秒以上アプリが背面化した場合は計測を自動停止する。90秒でも自動停止する。通常画面から「AI意味検索検証」のアイコンに戻ると計測を停止する。
5. AI検証画面へ戻ったら「メモリログの容量を更新」を押し、CSVに`screen=main`の行があることを確認する。通常画面を開かずに計測を中断した場合、`screen=main`が無いことがある。
6. 「RAM・通常画面の計測CSVを書き出す」で`lovely-ai-memory-lifecycle.csv`を任意の保存先へ書き出す。ログには測定数値と`screen`（poc/main/background/other）だけが含まれ、どの部屋・相手・チャット画面を開いたかは含まれない。
7. 同じ条件で**3回程度**繰り返し、バッテリー温度の変化・画面遷移・端末の操作感を別途観察する。必要であれば「RAM計測ログを削除する」で内部ログを消す（**既に外部へ保存したCSVは別途ユーザーが管理**）。

## 取得するCSVと測定値の解釈

新しいログ`filesDir/ai-poc/poc-memory-lifecycle-v1.csv`は既存の性能`poc-performance.csv`、実行条件`poc-run-modes-v1.csv`、品質`poc-quality-v1.csv`とは別ファイル。**従来のCSV形式・既存データを変更しない**。

| 列 | 意味 |
| --- | --- |
| `utc`, `run_id` | サンプル時刻と**検証操作ごとに生成したランダムなID**。端末個体識別IDではない |
| `phase` | `release_before` / `release_after_0` / `release_after_250ms` / `release_after_1000ms` / `release_after_3000ms` / `coexistence_transition` / `coexistence_sample` |
| `screen` | `poc`、`main`、`background`、`other`の大まかなActivity状態。**開いていたチャットルームは保存しない** |
| `elapsed_ms` | 各測定開始からの経過（wall clock） |
| `engine_loaded` | debug SDKエンジンの保持状態（true/false）。**RAM解放量そのものではない** |
| `pss_kb`, `native_pss_kb`, `dalvik_pss_kb`, `other_pss_kb` | Androidが推定する同一アプリプロセスのPSSと内訳。値はページの共有などで上下する |
| `private_dirty_kb`, `java_heap_kb`, `native_heap_kb` | プロセスのprivate dirty、Java実使用ヒープ、ネイティブヒープの割当量。互いに重なりうるため**単純合算しない** |
| `process_cpu_ms` | 測定開始からのプロセスCPU累積時間。隣り合う行の**差分**をwall clockの差分で割るとコア換算CPU使用率の近似 |
| `battery_percent`, `battery_temperature_c` | Androidのバッテリー残量・電池温度であり、AI単体の消費電力/SoC温度を直接測っていない |
| `thermal_status` | API29+のAndroid Thermal APIの段階値（0=NONE〜6=SHUTDOWN）。℃とは異なる。端末・OSの対応による |

通常画面の計測は最大**90秒／おおむね1秒ごと**。画面背面化後は最大5秒の移行猶予を設けて停止する。メモリ解放時の5点を含み、CSVは2MiBで上限。画面を復帰しても標本数が足りないことがあり、**サンプリング上のピークが真の瞬間ピークとは限らない**。ログ取得自体にも僅かなCPU/PSS負荷がある。

## セキュリティと採否

- SDKやActivityは`app/src/debug`だけ。本番APKへこの診断機能・CSVを含めない。
- **チャット本文、部屋名、メッセージ、相手の識別子、本家Cookie、pwd、HTTPリクエスト、モデルの絶対パスをログへ出さない。** `run_id`は性能CSVのrun_idとは別で、今回の実験内だけをつなぐランダムID。
- メモリ計測のために端末権限・常駐通知・WorkManager・追加通信を要求しない。通常のMainActivityを開いたことにより生じる通信はアプリの従来の通信規則の範囲。
- 通常画面でモデルを**解放した状態の互換性試験**が目的であり、モデルをロードしたまま実チャットへ渡す機能は追加していない。これを「AIと実チャットの同時推論成功」と誤って扱わない。
- 共有するならユーザーが選んだCSVだけ。実機CSVの生データは公開GitHubにコミットしない。Issue #110にまとめた集計値だけ記録する。
